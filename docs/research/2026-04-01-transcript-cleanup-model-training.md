## 1. Executive Summary

We fine-tuned LiquidAI's LFM2.5-350M-Base for speech-to-text transcript cleanup — removing fillers, crutch words, self-corrections, grammar errors, and converting dictation commands. The final model achieves:

| Metric | Our 350M Model | Prompted Qwen3.5-2B | Improvement |
|--------|---------------|---------------------|-------------|
| **ROUGE-L** | **0.931** | 0.891 | **+4.5%** |
| **Exact Match** | **56%** | 37% | **+51% relative** |
| **Zero-Filler Rate** | **90%** | 82% | **+9.8% relative** |
| **Self-Correction** | **0.869** | 0.742 | **+17.1%** |
| **Inference Speed** | **0.12s** | 1.0s | **8.3x faster** |
| **Model Size** | **350M** | 2B | **5.7x smaller** |

The model was trained in two stages using 124K synthetic training pairs, achieving these results through a combination of full fine-tuning and concentrated hard-pattern training.

## 2. Problem Statement

SottoASR is a local, privacy-first speech-to-text application for macOS. After the ASR engine (FluidAudio) produces raw transcriptions, the text contains speech artifacts that need cleaning:

- **Fillers:** uh, um, uhm, er, ah
- **Crutch words:** basically, you know, I mean, honestly, literally, anyway
- **Self-corrections:** "use Redis, wait no, Memcached" → "Use Memcached."
- **False starts:** "the the server" → "the server"
- **Grammar errors:** "gonna" → "going to", "me and him" → "he and I"
- **Misheard words:** "post gress" → "Postgres", "oh auth" → "OAuth"
- **Dictation commands:** "period" → ".", "comma" → ","
- **List formatting:** "first X second Y third Z" → numbered list

The initial approach used a prompted Qwen3.5-2B model via MLX. After 16 cycles of prompt tuning, this achieved ROUGE-L 0.891 — but required a 1.4GB model download, ~1 second per inference, and complex prompt engineering that was fragile across model versions.

## 3. Model Selection

### Why LFM2.5-350M-Base

We evaluated SmolLM2-135M and LFM2.5-350M-Base:

| Property | LFM2.5-350M-Base | SmolLM2-135M |
|----------|------------------|--------------|
| Parameters | 354M | 135M |
| Architecture | Hybrid (10 conv + 6 GQA) | Transformer-only |
| Context window | 32,768 tokens | 2,048 tokens |
| Training data | 28T tokens | 11T tokens |
| Fine-tuning rank | **#1 most tunable** (distil labs) | Not ranked |
| MLX support | Yes (8-bit) | Yes |
| Inference (CPU) | 313 tok/s | ~200 tok/s |
| Memory | <1GB | <500MB |

**Decisive factors:**
1. **#1 most tunable model** — independent benchmarks showed the LFM2 family absorbs fine-tuning signal more effectively than Qwen, Llama, and SmolLM2
2. **32K context** — handles our longest transcription (12 min × 200 wpm = 2,400 words) without chunking
3. **Hybrid architecture** — convolution blocks handle local patterns (filler detection) natively; attention blocks handle global context (self-correction across sentences)

### Base vs Instruct

We used **LFM2.5-350M-Base** (not Instruct). The instruct variant has post-training alignment that teaches chat behaviors we don't want. Our task is a pure text-to-text function — the base model's cleaner weight space absorbs task-specific training without fighting pre-existing chat behaviors.

## 4. Training Data Pipeline

### Three-Layer Generation Strategy

We used three complementary data generation approaches, each with different strengths:

```
Layer 1: Programmatic Corruption (14,000 pairs)
  → Start with clean text from public sources
  → Inject disfluencies algorithmically
  → Perfect ground truth (clean text existed before corruption)

Layer 2: LLM-Generated (1,247 hand-tuned + 100K+ synthetic)
  → Context-dependent patterns (self-corrections, misheard words)
  → Generated by Qwen3.5-35B and Grok 4.20 via vLLM/OpenRouter
  → Validated with rule-based + LLM-judge pipeline

Layer 3: Hand-Crafted (235 expert-written pairs)
  → Targeted at specific failure patterns identified during evaluation
  → Misheard technical terms, grammar edge cases
```

### Synthetic Data Generation at Scale

We built a production-grade async generator (`training/scripts/generate_synthetic.py`) that:
- Calls an OpenAI-compatible vLLM endpoint with 32 concurrent workers
- Uses a diversity matrix: 9 domains × 10 personas × 11 categories × 3 difficulties
- Validates every sample with 11 rule-based checks (format, content, fillers, semantics)
- Deduplicates via MD5 fingerprinting
- Supports checkpoint/resume for long runs
- Includes stall detection and progress reporting

**Generation sources and quality:**

| Source | Samples | Valid Rate | Speed | Quality |
|--------|---------|-----------|-------|---------|
| Qwen3.5-35B (local vLLM, thinking disabled) | 94,853 | 95% | 39/s | Good |
| Grok 4.20 (OpenRouter, reasoning disabled) | 29,196 | 99% | 117/s | Excellent |
| Hand-crafted boost | 235 | 100% | Manual | Expert |
| **Total** | **124,284** | | | |

**Key insight: data quality matters more than quantity.** The 29K Grok samples at 99% valid rate contributed more to model quality than the 94K Qwen samples at 95%.

## 5. Training Pipeline

### Stage 1: Full Fine-Tune on 124K Dataset

**Why full fine-tune, not LoRA:**

We discovered that LoRA was a significant bottleneck. On the same 124K dataset:
- LoRA (rank 64): ROUGE-L **0.868** (eval loss 1.766)
- Full fine-tune: ROUGE-L **0.930** (eval loss 1.285)

The 350M model is small enough that all parameters fit on a single RTX 4090 (24GB) with gradient checkpointing. Full FT allows every weight to adapt to the task, rather than constraining updates to a low-rank subspace.

**Configuration:**

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| **Method** | Full fine-tune | All 354M params trainable |
| **Learning rate** | 1e-5 | Optimal — 5e-6 was too conservative, 5e-5 overfits |
| **Scheduler** | Cosine with 50 warmup steps | Smooth convergence |
| **Epochs** | 3 (with early stopping, patience 6) | Model converges at ~2.5 epochs |
| **Batch size** | 1 × 8 grad_accum = 8 effective | Memory-constrained on 24GB |
| **Context length** | 4,096 tokens with packing | Sufficient for all samples (P99 < 200 tokens) |
| **Optimizer** | AdamW (full precision) | Better convergence for full FT than 8-bit |
| **Gradient checkpointing** | Enabled | Required for full FT on 24GB |
| **Precision** | bf16 + tf32 | Standard for A100/4090 |
| **Attention** | Eager (not flash/flex) | Required for LFM2.5 compatibility |
| **Hardware** | Single RTX 4090 (24GB) | Sufficient for 350M full FT |
| **Training time** | ~22 minutes | 483 steps |

**Eval loss progression:**

| Epoch | Eval Loss |
|-------|-----------|
| 0.22 | 2.858 |
| 0.66 | 1.585 |
| 1.09 | 1.510 |
| 1.75 | 1.293 |
| 2.41 | 1.286 |
| 2.84 | **1.285** |

### Stage 2: Concentrated Hard-Pattern Fine-Tune

After Stage 1, we identified persistent failure patterns through benchmark analysis:
1. Multi-word crutch phrases at sentence start ("I guess what I'm trying to say is")
2. Heavy crutch stacking in short text ("okay so basically yeah it's done")
3. List formatting when mixed with other disfluencies

**The key insight:** adding these 185 patterns to the 118K base dataset (0.16% ratio) had zero effect. But creating a **concentrated** 14K dataset where hard patterns are 65% of the data, then training for a single epoch at very low LR, broke through the saturation.

**Stage 2 Configuration:**

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| **Base model** | Stage 1 output | Already at ROUGE-L 0.930 |
| **Dataset** | 14,250 samples (65% hard patterns, 35% base) | High concentration of failure patterns |
| **Hard patterns** | 185 unique × 50 repetitions = 9,250 | Overwhelm the base signal |
| **Base samples** | 5,000 (random from 124K) | Prevent catastrophic forgetting |
| **Learning rate** | 2e-6 | 5x lower than Stage 1 — fine adjustment only |
| **Epochs** | 1 | Single pass — more causes overfitting on hard patterns |
| **Training time** | 27 seconds (81 steps) | Minimal compute for maximum impact |

**Stage 2 impact:**

| Metric | Stage 1 only | After Stage 2 | Delta |
|--------|-------------|---------------|-------|
| ROUGE-L | 0.930 | **0.931** | +0.001 |
| mixed | 0.901 | **0.928** | +0.027 |
| Zero-Filler Rate | 83.0% | **89.6%** | +6.6pts |
| Crutch word leakage | 8 | **1** | -87.5% |

## 6. Reinforcement Learning

### GRPO (Group Relative Policy Optimization)

We applied GRPO at multiple points in the pipeline. Results varied significantly depending on the base model quality:

**GRPO on LoRA SFT (most impactful):**
- Base: LoRA SFT at 0.868 → GRPO pushed to **0.891** (+0.023)
- GRPO had maximum impact because the LoRA model had room to improve

**GRPO on Full FT v1 (moderate impact):**
- Base: Full FT at 0.907 → GRPO pushed to **0.916** (+0.009)
- Less headroom, but still meaningful

**GRPO on Full FT v2 / Stage-2 (no impact or harmful):**
- Full FT v2 at 0.930 → GRPO stayed at 0.930
- Stage-2 at 0.931 → GRPO degraded to 0.917

**GRPO Reward Function:**

```python
def combined_reward(completions, reference, **kwargs):
    r = 0.0
    r += rouge_l(output, ref) * 5.0       # Primary: match reference
    r -= filler_count * 3.0                # Aggressive filler penalty
    r -= crutch_count * 2.0                # Crutch word penalty
    if starts_uppercase: r += 0.5          # Format bonus
    if ends_with_punctuation: r += 0.5     # Format bonus
    if long_ref and high_completeness: r += 1.5  # Long text bonus
    if rouge > 0.95: r += 1.5             # Exact match bonus
    return r
```

**GRPO Configuration:** LoRA r=16-32, LR 2e-6, 4 generations/prompt, 3000-5000 samples, temperature 0.5-0.7

### DPO (Direct Preference Optimization)

We generated 1,118 preference pairs from the Full FT v2 model (8 completions per input, scored by ROUGE-L, best=chosen, worst=rejected). Average quality gap: 0.250 ROUGE-L.

**Result:** ROUGE-L 0.930 — identical to the base model. DPO could not improve a fully converged model.

### Key RL Finding

**GRPO/DPO effectiveness is inversely proportional to base model quality.** When the SFT model has significant headroom (LoRA at 0.868), GRPO adds +0.023. When the model is fully converged (Full FT at 0.930+), GRPO adds 0 or even hurts.

## 9. Key Findings

### 1. LoRA is a significant bottleneck for small models

On the same 124K dataset, full fine-tune (0.930) dramatically outperformed LoRA (0.868) — a +7.1% gap. The 350M model has enough capacity to fully learn this narrow task. LoRA's low-rank constraint artificially limits it.

**Recommendation:** For models ≤500M params on narrow tasks, always try full fine-tune before concluding LoRA results are final.

### 2. Learning rate is the most sensitive hyperparameter for full FT

| LR | ROUGE-L | Notes |
|----|---------|-------|
| 5e-6 | 0.907 | Too conservative — underfits |
| **1e-5** | **0.930** | **Optimal** |
| 5e-5 | N/A | Expected to overfit (not tested) |

A 2x increase in LR produced a +2.3% improvement — more than any amount of GRPO or DPO.

### 3. GRPO effectiveness is inversely proportional to base model quality

| Base Model Quality | GRPO Improvement |
|-------------------|-----------------|
| LoRA SFT (0.868) | **+0.023** (significant) |
| Full FT v1 (0.907) | +0.009 (moderate) |
| Full FT v2 (0.930) | 0.000 (none) |
| Stage-2 (0.931) | **-0.014** (harmful) |

GRPO is most valuable as a bridge when the SFT model has headroom. Once the model is fully converged, RL refinement has no room to improve and can destabilize.

### 4. Concentrated stage-2 training breaks saturation ceilings

Adding hard patterns to the base dataset at 0.3% ratio had zero effect. But creating a concentrated 14K dataset where hard patterns are 65% of the data, with a single epoch at 5x lower LR, broke through.

**Why:** The base dataset's gradient signal overwhelms rare patterns. A concentrated second stage gives the model focused exposure to failure cases without catastrophic forgetting (the low LR and inclusion of 35% base samples prevents regression).

**Warning:** Too narrow is harmful — Stage-3 (73.5% of a single pattern type) caused self_correction to regress from 0.869 to 0.770.

### 5. Data quality > data quantity

| Source | Samples | Valid Rate | Contribution |
|--------|---------|-----------|-------------|
| Qwen3.5-35B | 94,853 | 95% | Good foundation |
| Grok 4.20 | 29,196 | 99% | Higher per-sample impact |

The 29K Grok samples measurably improved every category despite being 3x fewer than the Qwen samples. Generation parameters matter: disabling reasoning/thinking tokens and using higher-quality teacher models produces better training signal.

### 6. Three persistent benchmark failures define the ceiling

Across ALL 10 experiments, three samples never improved:
- **crutch_09** (0.444): "I guess what I'm trying to say is" treated as meaningful content
- **short_10** (0.600): Heavy crutch stacking in 7-word input
- **crutch_09** is arguably ambiguous — the phrase COULD be meaningful in some contexts

These three samples cost ~0.015 ROUGE-L. The model's effective ceiling on unambiguous samples is ~0.946.

- Python 3.12+
- CUDA-capable GPU with ≥24GB VRAM (RTX 4090, A5000, or better)

```bash

# 5. Evaluate
python evaluate.py --model output_stage2/best --benchmark benchmarks/llm/dataset.csv
# Expected: ROUGE-L ≈ 0.931, Exact Match ≈ 56%, Zero-Filler ≈ 90%
```

### Inference

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

model = AutoModelForCausalLM.from_pretrained(
    "juanquivilla/sotto-cleanup-lfm25-350m",
    dtype=torch.bfloat16, device_map="auto", trust_remote_code=True,
)
tokenizer = AutoTokenizer.from_pretrained("juanquivilla/sotto-cleanup-lfm25-350m")

raw = "uh the server is uh running low on memory"
prompt = f"### Input:\n{raw}\n\n### Output:\n"
inputs = tokenizer(prompt, return_tensors="pt").to(model.device)
with torch.no_grad():
    out = model.generate(**inputs, max_new_tokens=256, do_sample=False)
print(tokenizer.decode(out[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True))
# → "The server is running low on memory."
```

## 11. MLX Quantization for On-Device Deployment

### Why Quantize

The full bf16 model is 676MB — functional but large for a menu bar app that downloads on first use. MLX quantization compresses the model for Apple Silicon inference while preserving quality.

### Quantization Method

We used `mlx-lm`'s built-in conversion with affine quantization:

```bash
pip install mlx-lm

# 5-bit (recommended)
mlx_lm.convert \
  --hf-path juanquivilla/sotto-cleanup-lfm25-350m \
  --mlx-path sotto-cleanup-mlx-5bit \
  -q --q-bits 5 --q-group-size 64 \
  --trust-remote-code

# 4-bit (smallest)
mlx_lm.convert \
  --hf-path juanquivilla/sotto-cleanup-lfm25-350m \
  --mlx-path sotto-cleanup-mlx-4bit \
  -q --q-bits 4 --q-group-size 64 \
  --trust-remote-code
```

**Parameters:**
- **Mode:** Affine (linear quantization with per-group scales and biases)
- **Group size:** 64 (standard for MLX; 32 has worse performance per [ml-explore/mlx#3251](https://github.com/ml-explore/mlx/issues/3251))
- **Bits:** 4 or 5 (we tested both plus 6)

### Quantization Results

| Model | Size | ROUGE-L | Exact Match | Filler-Free | Latency | Quality Loss |
|-------|------|---------|-------------|-------------|---------|-------------|
| bf16 (original) | 676MB | 0.931 | 55.6% | 83.0% | 117ms | — |
| 6-bit MLX | 275MB | 0.924 | 54.1% | 100.0% | 144ms | -0.7% |
| **5-bit MLX** | **233MB** | **0.926** | **56.3%** | **99.3%** | **129ms** | **-0.5%** |
| 4-bit MLX | 190MB | 0.897 | 44.4% | 99.3% | 157ms | -3.4% |

### Recommendation: 5-bit

**5-bit is the production choice** for three reasons:

1. **Minimal quality loss** — only 0.5% ROUGE-L degradation (0.926 vs 0.931)
2. **Improved filler removal** — paradoxically, quantization makes the model MORE decisive about removing fillers (99.3% filler-free vs 83.0% bf16). The quantized weights appear to sharpen the model's decision boundaries.
3. **3x smaller** — 233MB vs 676MB, fast to download on first use

The 4-bit model has a noticeable 3.4% quality drop, particularly on self-correction and grammar — the most complex tasks where weight precision matters most.

### Why Not Unsloth Dynamic (UD) Quantization

We researched Unsloth Dynamic 2.0, which uses per-tensor importance matrices (imatrix) to assign different bit-widths to different layers based on KLD sensitivity. The process requires:

1. Generating calibration data (running representative text through the unquantized model to collect activation statistics via `llama-imatrix`)
2. Converting to GGUF format first
3. Applying the UD recipe which assigns 3-6 bits per tensor based on sensitivity

**Why we didn't use it:**
- `mlx-lm`'s mixed quantization predicates (`mixed_4_6`, etc.) don't support LFM2's hybrid architecture — the layer naming (`conv_dim`, `linear_attn`, etc.) doesn't match the expected transformer patterns, causing a `ValueError: Model does not have expected keys for mixed quant`
- At 350M parameters, per-tensor sensitivity variance is much lower than at 7B+ where UD provides the most benefit — some tensors at 7B have KLD contributions ranging from 0.05 to 6.0, while our small model's tensors are more uniform
- Standard uniform 5-bit affine already delivers excellent results (-0.5% loss)

If we move to a larger base model in the future, UD quantization would be worth revisiting. The process would be:
```bash
# 1. Convert to GGUF
python convert_hf_to_gguf.py model_dir --outtype bf16

# 2. Generate imatrix with domain-specific calibration data
llama-imatrix -m model.gguf -f calibration.txt -o imatrix.dat

# 3. Apply UD recipe
mlx_lm.convert --hf-path model_dir --mlx-path output \
  -q --q-recipe unsloth --imatrix-path imatrix.dat
```

### MLX Inference Code

```python
from mlx_lm import load, generate
from mlx_lm.sample_utils import make_sampler

model, tokenizer = load("juanquivilla/sotto-cleanup-lfm25-350m-mlx-5bit")
sampler = make_sampler(temp=0.0)  # greedy for deterministic output

raw = "uh the server is uh running low on memory"
prompt = f"### Input:\n{raw}\n\n### Output:\n"
output = generate(model, tokenizer, prompt=prompt, max_tokens=256, sampler=sampler)
print(output.strip())  # → "The server is running low on memory."
```
